- 2026-09-17 — Xcode project is generated from `project.yml` with XcodeGen; `VeraFlow.xcodeproj` is gitignored — M0 was written without access to Xcode; a YAML definition is reviewable and reproducible, and XcodeGen is a dev tool, not an app dependency (the FluidAudio-only rule is about linked packages) — Jeremy / Claude Code
- 2026-09-17 — Alpha builds use the same bundle ID as release, differing only in display name ("Riffle (alpha)") and the `ALPHA` compile flag — Keeps StoreKit product config and TestFlight simple; side-by-side installs aren't needed — Jeremy / Claude Code
- 2026-09-17 — FluidAudio pinned to exact version 0.15.7 (latest tag at time of M0) — SPEC §10.1 asks for an exact pin; bump deliberately in M4 after checking release notes — Claude Code
- 2026-09-17 — `AppServices.live()` returns fakes until each milestone lands its real service — Lets the app launch and the UI be built against protocols from M0; each milestone swaps one service — Claude Code
- 2026-09-17 — Building with Xcode 26.6 / iOS 26.5 SDK until Xcode 27 ships — That is what is installed; nothing through M4 needs iOS 27 APIs. M5 must gate `SystemLanguageModel.contextSize` and `tokenCount(for:)` behind `#available(iOS 27, *)` and also compile-time `#if canImport` checks if the SDK still lacks them — Jeremy / Claude Code
- 2026-09-17 — M1 recorder uses the classic `AVAudioEngine.connect`, `installTap`, and `AVAudioSession.interruptionNotification` APIs — Apple's docs mark them deprecated in iOS 27 in favour of `connectNode`, `AVAudioSession.InterruptionContext`, and friends, but those replacements are iOS 27-only and absent from the iOS 26.5 SDK we build with. Revisit when Xcode 27 is in use: gate the new calls behind `#available(iOS 27, *)` — Claude Code
- 2026-09-17 — Recorder graph is a tap on `inputNode` in its native format, converted per buffer with `AVAudioConverter` to mono 44.1 kHz float; no output path — First attempt routed input → mixer → muted main mixer and tapped the mixer, and on device the file came out silent. Tapping the input directly is Apple's documented pattern and doesn't depend on the engine pulling audio through an output — Claude Code
- 2026-09-17 — Launch recovery marks an interrupted recording `.failed` (not `.recorded`) when its audio file is missing or unreadable — SPEC §8.2 says mark `.recorded`, but a row that can't play or transcribe would just fail later with a worse message; readable files are marked `.recorded` as specified — Claude Code
- 2026-09-17 — Capture format is AAC in an ADTS stream (`audio.aac`), not AAC in CAF as SPEC §8.2 says — Verified on device: a force-quit mid-recording left the CAF/AAC file unreadable (181 KB on disk, AVAudioFile refused it) because Core Audio writes the CAF packet table only on close. ADTS frames each carry a header, so a truncated file plays up to the last whole frame; same codec, sample rate, and ~64 kbps. Unit test truncates an ADTS file and reads it back. Rows created before this change keep their `audio.caf` name and still resolve — Jeremy / Claude Code
- 2026-09-17 — Share-sheet import uses document types + `onOpenURL` (system copies the file to Documents/Inbox), not a Share Extension — Same user-visible result ("VeraFlow" in the share sheet / "Open in"), no second app target, no app group, no extra signing. Revisit only if a "share without leaving the other app" flow is wanted — Jeremy / Claude Code
- 2026-09-17 — Imported files keep their original container (`audio.m4a`, `audio.wav`, ...) rather than being transcoded to ADTS — The crash-safety reason for ADTS applies to live capture only; playback and transcription read any of the supported containers, and copying is instant where transcoding a 60-minute file is not — Claude Code

- 2026-09-17 — Every restart of capture (Resume, configuration change, media-services reset) discards the `AVAudioEngine`, builds a new one, re-reads the input node's output format (retrying briefly while it reads 0 Hz after a route change), and only then installs a tap — The 90-minute device test was interrupted at 43:42 and crashed on Resume. The crash log shows an Objective-C exception inside `installTap`, reached from the configuration-change handler re-tapping an engine that Resume had just started. `installTap` cannot be caught from Swift, so the conditions it rejects are checked first and the engine is always stopped before re-tapping; a bad state degrades to "Paused, tap Resume" instead of a crash. A fresh engine is required, not just a stopped one: re-tapping a running engine is what raised the exception. A first version also demanded that the node's output format equal the hardware format; on device those legitimately differ after a Bluetooth switch (session at the headset's 16 kHz, hardware reporting the iPhone mic's 48 kHz), which left Resume stuck, so the tap simply uses the node's output format as Apple's samples do. The interruption reason is now logged so the next pause can be explained — Claude Code
- 2026-09-17 — Playback duration comes from `AudioFileInfo.duration(of:)` (frame count), not `AVAudioPlayer.duration` — For ADTS streams the player's duration is a bit-rate estimate and showed 42:22 for a 43:42 recording; the frame count matches the recorder's timer — Claude Code
- 2026-09-17 — Recording Live Activity (Lock Screen banner + Dynamic Island: timer, Recording/Paused, bookmark count) is built in M1, status only, as a `VeraFlowWidgets` app-extension target sharing `Shared/RecordingActivityAttributes.swift` with the app — SPEC §16 lists it as a v1.1 stretch item; Jeremy asked for it after the first long device test. Status only (no Lock Screen buttons) keeps it to ActivityKit + one widget target; buttons would add App Intents and are a later step. The extension has no network, no app group, and no push token — Jeremy / Claude Code
- 2026-09-17 — With a Bluetooth headset connected, the recorder prefers the iPhone's built-in mic unless the user picks the headset (or "Automatic") in the Microphone menu; the choice is remembered — iOS otherwise routes recording through the headset's 16 kHz call profile, which sounds worse than the phone for a meeting, and on device the earbuds' mic went silent whenever they weren't worn. The menu is on the Record screen before and during recording; switching mid-recording restarts capture on the new input without a pause — Jeremy / Claude Code
- 2026-09-17 — Transcription runs behind `EngineSelectingTranscriptionService`, which routes each call to Apple Speech (default) or FluidAudio Parakeet according to a `UserDefaults` preference that only the DEBUG "Transcription benchmark" screen (Settings → Developer) can change — SPEC §9.4 asks for Parakeet behind a debug flag and a benchmark on the fixtures. One selector in front of two real services means the pipeline, the progress events, and the transcript screen are identical for both engines, so the comparison is fair and switching the shipped engine later is one line in `AppServices.live`. Release builds always use Apple Speech until the benchmark result is recorded here — Jeremy / Claude Code
- 2026-09-17 — Apple Speech asset downloads and `DictationTranscriber` fallback are handled inside `LiveTranscriptionService`; the reserved locale is kept for the app's lifetime rather than released after each file — SPEC §9.2 suggests releasing unused locales, but the app only ever transcribes in the user's locale and re-reserving it per file adds a slow, failure-prone step for nothing. Revisit if a per-recording language choice is added — Claude Code
- 2026-09-17 — Background processing uses `BGContinuedProcessingTaskRequest` (iOS 26) with the `.fail` strategy and an inline fallback when the system won't grant it; Core ML engines (Parakeet now, the diarizer in M4) may still be throttled in the background on iOS 27 without the `com.apple.developer.background-tasks.continued-processing.inference` entitlement, which we don't hold yet — Apple Speech is not affected, so the shipped pipeline works either way; the entitlement request is queued for M4 when the diarizer lands. Until then, the benchmark screen tells the tester to keep the app in the foreground — Claude Code
- 2026-09-17 — Transcript search is a text field in the transcript header, not `.searchable` — The detail screen is pushed from the Library, which already owns the navigation bar's search field; a second `.searchable` on a pushed view fights it on iOS 26. The in-page field also keeps the match count and the Edit button together — Claude Code
- 2026-09-17 — The M4 aligner (`LiveTranscriptAligner`) is a port of the Antigravity branch's `TranscriptAligner` (largest overlap, nearest turn within 0.5 s, previous-speaker fallback, short-run smoothing, keys by first appearance), re-fitted to our `TranscriptAligning` protocol and `Paragrapher.Rules`, with its six tests ported and three added — The review found that module sound; porting it with credit beats rewriting it. The rest of that branch stays unmerged as reference — Jeremy / Claude Code
- 2026-09-17 — Diarization never blocks a recording: on any failure (models missing, download refused, FluidAudio error) the transcript keeps a single "Speaker 1", the stage still advances to `.diarized`, and the reason is kept in `failedStage`/`failureMessage` so the transcript shows "Speaker labels couldn't be added" with Retry — SPEC §6.3 and M4's "failure path shows a single speaker + retry". Marking the row `.failed` would have hidden a perfectly readable transcript behind an error — Claude Code
- 2026-09-17 — When the user has already edited a transcript, diarization labels the existing paragraphs by majority vote of their words (`speakerKeys(forSegments:turns:)`) instead of rebuilding paragraphs by speaker — Re-splitting would discard the edits. Unedited transcripts are re-split per SPEC §10.2 so speaker changes start new paragraphs — Claude Code
- 2026-09-17 — `LiveDiarizationService` loads FluidAudio's `OfflineDiarizerModels` once per launch and creates a fresh `OfflineDiarizerManager` per file with the "Expected speakers" hint in `config.clustering.numSpeakers` / `minSpeakers` — The manager isn't Sendable and its config is fixed at init; the models struct is Sendable and holds the expensive part. "4 or more" maps to `minSpeakers = 4` rather than forcing an exact count — Claude Code
- 2026-09-17 — M5 is split: the deterministic half (due dates, chunking, budget, post-processing, prompts, the summarizing stage, the Summary tab) is written against the `SummarizationService` protocol with the fake, and the Foundation Models service comes after the M3/M4 compile round — Every Foundation Models API name must be verified against the SDK on Jeremy's Mac (CLAUDE.md), and the iOS 26.5 SDK may lack iOS 27 calls. Everything else in §11 is plain Swift and fully testable now. Until the real service lands, `AppServices.live` keeps the fake summarizer, which is clearly labelled "FakeSummarizationService" in each summary's Model row — Claude Code
- 2026-09-17 — The summarizing stage never fails a recording: with the on-device model unavailable (or a generation error) the row still becomes `.ready`, the reason is kept in `failedStage`/`failureMessage`, and the Summary tab offers Retry — SPEC §15: transcripts must work on every iPhone; a `.failed` row would hide a good transcript. The stage also leaves an earlier non-fatal speaker-label reason in place — Claude Code
- 2026-09-17 — `LiveDueDateResolver` resolves "next <weekday>" to that weekday in the following Monday-to-Sunday week, "next week" to Monday, "end of week" to Friday, a bare weekday to its next occurrence (today included), phrases without a time to 5 PM, and month/day phrases to their next occurrence after the recording date; `NSDataDetector` is only a fallback and only its month and day are used — SPEC §11.6 fixes some of these; the rest follows common business usage and the Antigravity review's corrections. All of it is table-tested against a fixed Thursday so results never depend on the day the tests run — Claude Code
- 2026-09-18 — `LiveSummarizationService` catches `LanguageModelSession.GenerationError` (iOS 26 API) and uses `GenerationOptions(sampling:temperature:maximumResponseTokens:)` — Apple's reference now marks both deprecated in the iOS 27 SDK (replaced by `LanguageModelError.contextSizeExceeded` and the `samplingMode:` initializer, back-deployed), but we build with Xcode 26.6 / iOS 26.5 SDK where only the older names exist. Apple says apps must migrate before submitting with Xcode 27, so this is a listed M9 task. `contextSize` is back-deployed to iOS 26.0 and is read at runtime; `tokenCount(for:)` (iOS 26.4+) is used behind `#available` to count instructions and schemas and to calibrate the chars ÷ 3.5 estimate with one real count of the transcript — Claude Code
- 2026-09-18 — Chunking uses a synchronous token estimate scaled by one real `tokenCount` of the whole transcript, never below the conservative estimate — Counting every line asynchronously would cost hundreds of model calls per summary; one calibration call keeps chunks honest while the chunker stays pure and testable — Claude Code
