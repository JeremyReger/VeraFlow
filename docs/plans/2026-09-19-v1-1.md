# v1.1 plan — the promised items and the bigger bets

Written 2026-09-19 from the feature review of the full project. Scope: the ten items the spec or the design already promise but the build doesn't keep yet, plus the five bigger bets, and two items added after Jeremy's caveats: the Mac before the iPad, and older iPhones on Parakeet. The "additions that change the pitch" tier (action item inbox, "this is me", known voices, calendar titles, walk-through photos, vocabulary, Shortcuts, email for every template, SRT) is queued for v1.2 and is not planned here.

Ground rules carried over from CLAUDE.md: one milestone at a time, plan before code, every change with tests, `scripts/test.sh` green before commit, verify every Apple and FluidAudio signature against the SDK before using it, nothing leaves the phone.

## How the plan is organised

Each item below has the same shape: what it is, why it's in 1.1, the design (data, services, UI), the files it touches, the tests, the device checks for Jeremy, the size, and what must be verified against the SDK before coding. Sizes are agent working days including tests, not counting Jeremy's device time:

| Size | Meaning |
|---|---|
| S | Under a day |
| M | One to three days |
| L | Three to six days |

The schedule at the end groups the seventeen items into seven waves, each its own branch and PR, in the order that keeps the promises first and the risk last.

## Cross-cutting decisions to make first

These affect several items and should be settled before Wave A starts.

1. **One schema version, early.** Six items add stored fields (mark kind, trash date, sample source, translated text, custom templates, chapter starts inside the payload). TestFlight users already have data, so 1.1 introduces `VeraFlowSchemaV2` as a SwiftData `VersionedSchema` with a `SchemaMigrationPlan`, added in Wave A with all the new optional fields at once. Every later item then adds nothing to the store. Adding optional properties is a lightweight migration, but naming the version now means 1.2 can do a custom migration if it ever has to.
2. **One prompt bump.** Marks, chapters and the per-recording focus all change the prompts. They ship together as prompt v3, so `modelInfo` moves once and the golden runs are done once. `docs/EVALS.md` doesn't exist yet even though SPEC §16 M5 asks for it; Wave B creates it.
3. **Free versus unlocked.** Proposed additions to the SPEC §13.2 table. Jeremy decides.

| Feature | Free | Unlocked |
|---|---|---|
| Speaker filter, skip silence, trash, notification, language picker, live transcript, marks | Yes | Yes |
| Library archive export and import | **Yes** (data portability is never behind a paywall) | Yes |
| Editing action items | Yes (the three free summaries are editable) | Yes |
| Chapters | With the summary | Yes |
| Ask this recording | No (the sample recording answers unlimited questions so the feature can be tried) | Yes |
| Custom templates, focus line | No | Yes |
| Translation | No | Yes |

4. **Mac then iPad, and where 1.1 stops.** Jeremy's order is Mac first (item 15). The Mac is a native target with universal purchase, and the iPad reuses its split layout. Both sit at the end of the schedule; the recommendation is to cut 1.1 after the Mac if the waves run long and let the iPad open 1.2.
5. **Older iPhones.** Item 16 lowers the floor to iOS 18 with Parakeet as the transcription engine there. It does not bring summaries to phones without Apple Intelligence; only a bundled model would (item 17, investigation only in 1.1).
6. **Backup default stays off.** Item 5 adds an "include in iPhone backup" switch. Off by default keeps the "nothing leaves the phone unless you say so" promise; the copy says the backup is Apple's, end-to-end encrypted when Advanced Data Protection is on, and that VeraFlow itself still makes no network request.

## Part 1 — promised but not built

### 1. Marks feed the summary and show in the transcript

**What.** The Mark button drops a flag while recording. Today the flag is listed on the Audio tab and nowhere else. After this item, marks appear in the transcript at their moment, carry an optional one-word label, and the summarizer is told about them so a marked moment is weighted and cited.

**Why.** The design spec says the summary weights marked moments, and calls Mark "the thing people actually want mid-meeting." Design open question 2 (transcript marker or a list for the summary) is answered: both.

**Design.**
- Data: `Bookmark` gets `kind: BookmarkKind` (`.manual`, `.interrupted`, room for `.photo` in 1.2) with a default of `.manual` for existing rows, and `note` becomes the label. The "Interrupted" bookmark stops relying on its note text.
- Recorder: after Mark, a small chip row appears for three seconds with four labels (Decision, To-do, Quote, Question). Tapping one sets the note; ignoring it leaves a plain mark. The Live Activity's Bookmark intent stays label-less. The chip row is its own `View` like `MicrophoneMenu`, so the 10 Hz redraws don't rebuild it.
- Summarizer: `SummarizationInput` gains `marks: [MarkLine]` (time, label). `TranscriptChunker` renders them as `[mm:ss] ★ Marked: Decision` lines in time order between transcript lines, so a chunk that holds the moment also holds the mark, and the budget counts them. Interrupted marks are excluded. `Prompts.sharedRules` (v3) adds one sentence: lines starting with ★ are moments the user flagged as important; give them weight and cite their time. No new output fields, so nothing for the model to invent.
- Transcript tab: a marker row (flag glyph, label, time) inserted before the first paragraph that starts after the mark time; tap seeks. Marks are included in the speaker-filtered view (item 3) regardless of speaker.
- Exports: Markdown and PDF list marks under a "Marked moments" heading when any exist.

**Files.** `Persistence/Models/Bookmark.swift`, `Services/Summaries/SummarizationInputBuilder.swift`, `TranscriptChunker.swift`, `Prompts.swift`, `Features/Recorder/RecorderView.swift` + `RecorderViewModel.swift`, `Features/RecordingDetail/TranscriptTab.swift`, `Services/Exports/ExportRenderer.swift`.

**Tests.** Chunker: marks land in the right chunk and never split a line; budget counts them. Input builder: interrupted marks excluded, labels substituted. Transcript: marker placement between paragraphs (pure function over segment starts). Renderer: marked-moments section. Recorder VM: label applies to the last mark only within the window.

**Device.** Record a five-minute conversation, mark three moments with labels, confirm the summary's key points or action items cite those times and the transcript shows the flags.

**Size.** M. **Verify first.** Nothing new from the SDK.

### 2. Editable action items, owners, and due dates

**What.** Tap an action item to change its task text, owner, or due date; add an item by hand; delete one. SPEC §11.6 says the resolved date can be edited; nothing is editable today.

**Design.**
- Data: the model's output in `payloadJSON` is never modified. `ActionItemsState` (already the editable overlay in `actionItemsState`) gains `overrides: [UUID: ActionItemOverride]` (task, owner, ownerSpeakerKey, dueDate, or `clearDueDate`), `added: [ActionItem]`, and `removed: Set<UUID>`. A pure `SummaryPayload.resolvedActionItems(applying:)` produces the list every screen and export uses. Edits belong to the summary record they were made on; a re-run with another template starts clean. Document that in DECISIONS.
- UI: an edit sheet from the item row with a text field, an owner picker (each speaker by display name, "No one", or free text), a due-date toggle with a `DatePicker`, and Delete. "Add action item" at the end of the list; manual items have no timestamp and no ▶︎. The completed strike-through and the reminder-sent state keep working by item ID.
- Reminders: an item already sent to Reminders isn't updated when edited in 1.1; the sheet says so. Updating existing reminders is a 1.2 line.
- Owner "Me": when 1.2's "this is me" lands the picker gains that entry; nothing to do now.

**Files.** `Services/SummaryPayload.swift`, `Features/RecordingDetail/SummaryTab.swift` (+ new `ActionItemEditor.swift`), `Services/Exports/ExportRenderer.swift`, `Features/Exports/ExportViews.swift` (Reminders sheet reads resolved items).

**Tests.** Overlay resolution (override, add, remove, ordering, unknown IDs ignored), encoding round-trip with old state data (no `overrides` key decodes fine), renderer and reminder requests use the resolved list.

**Device.** Fix an owner and a due date, add an item, send to Reminders, confirm the reminder shows the edited values.

**Size.** M. **Verify first.** Nothing new.

### 3. Speaker filter in the transcript

**What.** A row of chips under the transcript search (All, then one per speaker). One chip shows only that speaker's paragraphs, each still playable; the count reads "12 paragraphs · 4:52 of talk time". The Audio tab's talk-time rows open the transcript already filtered. Already requested and shaped in PROGRESS.

**Design.** A pure `TranscriptFilter` (speaker key, search text) over ordered segments, composing with the existing search. Playback is unchanged: "Play from here" plays the audio normally; only the list is filtered. The current-paragraph highlight follows the playhead only when the playing paragraph is visible. Chips use the speaker colours and names, never colour alone. Selecting a chip announces the count for VoiceOver.

**Files.** New `Features/RecordingDetail/TranscriptFilter.swift`, `TranscriptTab.swift`, `AudioTab.swift` (talk-time row navigation), `TalkTime.swift` reuse for the duration.

**Tests.** Filter (5): by speaker, by text, both, empty result, talk time equals `TalkTime` for that speaker. UI test: seeded transcript, tap a chip, count text changes.

**Device.** Two-speaker recording, filter to one, play from a paragraph.

**Size.** S. **Verify first.** Nothing new.

### 4. Live transcript while recording

**What.** Words appear on the Record screen about ten seconds into a recording, as the design draws it (previous line dimmed, current line full strength). The final, timed transcript still comes from the file pass after Stop.

**Design.**
- Service: `LiveTranscriptPreview` actor behind a `TranscriptPreviewService` protocol with a fake. It builds its own `SpeechAnalyzer` with a `SpeechTranscriber(locale:transcriptionOptions:reportingOptions: [.volatileResults] , attributeOptions: [])`, feeds it an `AsyncStream<AnalyzerInput>` from the recorder's tap (buffers converted with the existing `BufferResampler` to the analyzer's best available format), and publishes a small `PreviewState`: the last finalized lines (bounded to five) plus the current volatile line. Nothing is persisted.
- Recorder: `LiveAudioRecorderService` gets a second consumer of the tap buffers (a `Sendable` closure or an `AsyncStream` continuation) that the view model hands to the preview. Every capture restart (route change, interruption) restarts the preview stream too. Pause stops feeding; Resume continues with the same analyzer.
- Limits: preview runs only with `SpeechTranscriber` (not the dictation fallback), stops when the app goes to the background (recording continues; the file pass makes the real transcript anyway) and when `ProcessInfo.thermalState` reaches `.serious`, and is a Settings toggle ("Show words while recording", default on). No speaker tags live; diarization is offline. That is a deviation from the design's speaker-tagged live line; record it.
- Screen: the design's two-line block under the waveform. Live text is `accessibilityHidden` behind a single "Live transcript" element that reads the current line, so VoiceOver isn't flooded.

**Files.** New `Services/TranscriptPreviewService.swift` (protocol + fake), `Services/Live/LiveTranscriptPreview.swift`, `Services/Live/LiveAudioRecorderService.swift` (buffer fan-out), `Features/Recorder/RecorderViewModel.swift`, `RecorderView.swift`, `Support/AppPreferences.swift`, `Features/Settings/SettingsView.swift`.

**Tests.** A pure `PreviewReducer` (volatile replaces, finalized appends, bounded history, pause drops input) with tests; recorder VM with the fake preview (starts, pauses, stops on background, stops on thermal).

**Device.** Thirty-minute recording with the preview on: words appear within ~10 s, no thermal warning, battery drop noted; switch mic mid-recording and confirm the preview resumes; compare the final transcript's word count with a run done with the preview off.

**Size.** L. **Verify first.** `SpeechAnalyzer` streaming input (`AnalyzerInput(buffer:)`, `analyzeSequence(_:)` on an `AsyncSequence` versus `start(inputSequence:)`), `SpeechAnalyzer.bestAvailableAudioFormat(compatibleWith:)`, the `.volatileResults` reporting option, and whether two analyzers (preview now, file pass later) may hold the same reserved locale.

### 5. Library archive, single-recording packages, and the backup switch

**What.** Two things the spec promised in different places: a way to keep or move the library (no way today; recordings are excluded from backup), and the SPEC §6.2 "include in backup" toggle. Without this a buyer who gets a new iPhone loses every recording.

**Design.**
- Format: a package directory `<name>.veraflowarchive/` with `manifest.json` (format version, app version, created date, recording count) and `recordings/<uuid>/` holding the audio file as-is plus `recording.json` (title, dates, duration, source, locale, template, tags, favourite, engine, segments with words, speakers, bookmarks, summaries with payload, state and model info). The package UTType is declared in `project.yml` (conforms to `com.apple.package`), so Files shows it as one item and AirDrop moves it whole. No zip, no dependency; Apple Archive stays an option if Files handling of packages disappoints on device.
- Export: Settings → Storage → "Export library…" writes the package to `tmp/Exports/` then hands it to `UIDocumentPickerViewController(forExporting:)` so the user picks the folder (iCloud Drive, a USB drive, any file provider). Progress with a cancel. "Export recording…" in a row's menu writes a single-recording package the same way.
- Import: `fileImporter` accepting the package type (and the same `onOpenURL` path as audio files). Recordings whose ID already exists are skipped unless the user picks "Replace". A recording whose audio is missing from the package still imports with its transcript and summary and is marked "audio not available" (the same state the parked auto-archive idea needs, so build the flag now: `Recording.audioAvailable`).
- Backup switch: "Include recordings in iPhone backup" in Settings → Storage. Uses the existing `RecordingStorage.setExcludedFromBackupForAll(_:)` and `folder(for:excludeFromBackup:)`; new folders follow the preference. Copy: the backup is Apple's iCloud or Finder backup, VeraFlow still makes no network request, and the switch is off unless you turn it on.
- Storage row: total size of recordings (audio versus everything else), which the parked auto-archive request also wanted.

**Files.** New `Services/ArchiveService.swift` (protocol, fake) and `Services/Live/LiveArchiveService.swift` (`ArchiveWriter`, `ArchiveReader`, pure `RecordingSnapshot` Codable), `Persistence/RecordingStorage.swift`, `Persistence/Models/Recording.swift` (`audioAvailable`), `Features/Settings/SettingsView.swift` (+ `StorageView.swift`), `Features/Library/LibraryActions.swift` (import path), `project.yml` (UTType, document type), `Support/AppPreferences.swift`.

**Tests.** Snapshot round-trip for every model field including words and summaries; archive write then read in a temp directory recreates equal rows in an in-memory container; skip versus replace; missing audio imports as not-available; a newer format version is refused with a clear message; backup preference applies to new folders.

**Device.** Export the library to iCloud Drive, delete a recording, import the package, confirm the recording is back and plays; AirDrop a single-recording package to a second iPhone if one is available; flip the backup switch and check the folder's exclusion attribute in Diagnostics.

**Size.** L. **Verify first.** `UIDocumentPickerViewController(forExporting:asCopy:)` behaviour with a package directory, `UTType` package declaration keys in Info.plist, `fileImporter` with a package type.

### 6. Local notification when processing finishes

**What.** When a recording's summary becomes ready (or a stage stops and needs the user) while the app isn't in the foreground, post one local notification. Tapping it opens the recording. SPEC §15's expiry fallback mentions a prompt; nothing uses notifications today.

**Design.**
- Permission: request **provisional** authorization the first time a recording is still processing when the app goes to the background. Provisional notifications arrive quietly in Notification Center with no permission prompt; the user can promote them from there. Settings → Recording gets "Notify when a summary is ready", which requests full authorization when turned on.
- Content: title "Summary ready" or "Needs attention", body is the recording title only. Never transcript or summary text; the Lock Screen is exactly where the STIG review didn't want content. `userInfo` carries the recording ID; `AppState` opens it on tap.
- Decision logic is a pure `ProcessingNotifier.decide(from: old stage, to: new stage, appActive: Bool) -> Notification?` so it's testable; the coordinator's existing event stream drives it. Pending notifications for a recording are cleared when the user opens it.

**Files.** New `Services/NotificationService.swift` (protocol, fake) and `Services/Live/LiveNotificationService.swift`, `Support/ProcessingNotifier.swift`, `App/AppState.swift`, `Features/Settings/SettingsView.swift`.

**Tests.** Decide table: ready while backgrounded → notify; ready while active → nil; failed → needs attention; free-limit stop → needs attention; duplicate transitions → one.

**Device.** Start a recording, stop, lock the phone, wait; the notification appears without a prompt; tap opens the recording.

**Size.** S. **Verify first.** `UNAuthorizationOptions.provisional` and `UNUserNotificationCenter` delegate on the main actor under Swift 6.

**Tests.** Importing the bundled sample creates one recording with segments, two speakers, a summary, and the sample source; importing twice doesn't duplicate; the free counter is untouched.

**Device.** Fresh install, tap the sample button, read the summary, play the audio.

**Size.** S for code, plus Jeremy's recording session. Depends on item 5. **Verify first.** Nothing new.

### 8. Transcription language picker

**What.** Settings → Recording → "Transcription language": the iPhone language by default, or any locale Apple Speech supports on this phone. A row's menu gets "Transcribe again in…" for one recording. SPEC §15 asks for a picker over the supported list.

**Design.**
- `AppPreferences.transcriptionLocale` (BCP-47 or nil for the device). The list comes from `SpeechTranscriber.supportedLocales` with the dictation list as the fallback set, shown with `Locale.current.localizedString(forIdentifier:)` and grouped by installed versus needs download. Picking a locale that needs assets runs the existing `prepareAssets(for:)` with progress right there.
- New recordings store the chosen locale in `Recording.localeIdentifier` (already present). Re-transcribing resets segments, speakers and summaries after a confirmation that names what is lost (edits, labels, summaries).
- Summaries: if the transcript language isn't one the on-device model supports, the summarizing stage parks the row with a clear reason rather than trying. Check `SystemLanguageModel.supportsLocale(_:)` (or whatever the SDK names it).

**Files.** `Support/AppPreferences.swift`, `Features/Settings/SettingsView.swift` (+ `LanguagePicker.swift`), `Services/Live/LiveTranscriptionService.swift` (locale from the recording, already threaded), `Services/Live/LivePipelineCoordinator.swift` (retranscribe entry point), `Features/Library/RecordingActionsController.swift`.

**Tests.** Locale resolution (preference → recording), display names, retranscribe clears derived rows and re-queues from `.recorded`, unsupported summary locale parks with the reason.

**Device.** Pick Spanish, download the assets, record a short Spanish clip, confirm the transcript; switch back.

**Size.** S. **Verify first.** `SpeechTranscriber.supportedLocales` and `DictationTranscriber.supportedLocales` shapes, `SystemLanguageModel` locale support API name.

### 9. Skip silence in playback

**What.** A toggle on the Audio tab's transport row that jumps over pauses longer than about a second and a half, with "saves 4:12" next to it. SPEC §4.4 stretch item; the peaks are already computed.

**Design.** A pure `SilenceDetector.ranges(levels:bucketDuration:threshold:minimumGap:padding:)` over 100 ms level buckets read once per recording by the `WaveformPeaks` file reader (extend it to return the fine levels alongside the bars). Threshold is relative to the file's median level so quiet rooms and loud ones both work. `AudioPlayerController.tick` seeks to the end of a silent range when the playhead enters one; the mini player and the Now Playing elapsed time follow. The preference is remembered. Ranges are cached in memory per recording, not stored.

**Files.** `Support/WaveformPeaks.swift`, new `Support/SilenceDetector.swift`, `Features/RecordingDetail/AudioPlayerController.swift`, `AudioTab.swift`, `Support/AppPreferences.swift`.

**Tests.** Detector on synthetic level arrays (gap below the minimum ignored, padding kept, leading and trailing silence, all-silent file); player skips with a scripted tick; "saves" total equals the sum of ranges.

**Device.** A recording with long pauses plays through them noticeably faster; transcript highlight keeps up.

**Size.** S. **Verify first.** Nothing new.

### 10. Trash instead of delete

**What.** Deleting a recording moves it to Recently Deleted for 30 days; it can be restored or deleted for good; the sweep happens at launch. Delete is confirm-then-gone today.

**Design.** `Recording.deletedAt: Date?`. Every library query, search and the pipeline queue exclude trashed rows; trashing cancels processing like delete does now. A "Recently Deleted" screen under Settings → Storage lists trashed rows with days remaining, Restore and Delete Now, and "Empty". `TrashSweeper.sweep(now:)` runs beside `RecordingRecovery` at launch and removes folders past 30 days. "Delete all data" empties the trash too. The audio file stays on disk while in the trash, so the Storage row counts it under "Recently Deleted".

**Files.** `Persistence/Models/Recording.swift`, `Features/Library/LibraryActions.swift` (`trash`, `restore`, `deletePermanently`), `LibraryFilter.swift`, new `Persistence/TrashSweeper.swift`, `Features/Settings/RecentlyDeletedView.swift`, `Services/Live/LivePipelineCoordinator.swift` (skip trashed).

**Tests.** Filter excludes trashed; restore returns the row to the list; sweep removes only rows older than 30 days and their folders; delete-all empties the trash; a trashed row in `.transcribing` is cancelled.

**Device.** Delete, find it in Recently Deleted, restore, play.

**Size.** S. **Verify first.** Nothing new.

## Part 2 — bigger bets

### 11. Ask this recording

**What.** A question box on a recording: "What did Dave say about the permit?" answered on device from the transcript, with every answer citing a timestamp or saying "Not in the transcript." Unlocked-only per the table above; the sample recording answers freely.

**Why the guardrails matter here.** This is the one feature where the model is asked to produce free text about the recording, so the grounding has to be mechanical, not a prompt request.

**Design.**
- Retrieval, pure Swift: `TranscriptRetriever` scores paragraphs with BM25 over lowercased, stopword-stripped tokens (speaker names included as tokens so "what did Dave say" biases to Dave's lines), takes the top paragraphs with one neighbour each side, dedupes, orders them chronologically, and fills the existing `ContextBudget` minus the answer reserve. Marks (item 1) that fall inside chosen paragraphs are included.
- Generation: a fresh `LanguageModelSession` per question with a `@Generable struct GroundedAnswer { answer: String; citations: [String] /* mm:ss */; foundInTranscript: Bool }`. Instructions: answer only from the excerpts; cite the line times; if the excerpts don't answer it, set `foundInTranscript` false and leave `answer` empty; never compute a date, repeat the spoken phrase instead.
- Validation, pure Swift: each citation must parse and land inside a retrieved paragraph; an answer with `foundInTranscript` false or zero valid citations is shown as "Not found in this recording" with the top retrieved paragraphs offered as "Closest lines". The free text is never shown without a valid citation.
- UI: a fourth tab, "Ask", with suggested questions built from the summary (open questions, each action item's owner), an answer card with tappable timestamps, and a session history kept in memory for the recording. Rate-limit and timeout handling reuse `LanguageModelErrorBridge`. The AI disclaimer sits under every answer.
- Evals: `docs/EVALS.md` gets ten questions per fixture, three of them traps that aren't in the transcript, with the expected outcome (answered with a correct time, or not found). Ship only when the traps come back "not found" every time on the device.

**Files.** New `Services/QuestionAnswering/` (`TranscriptRetriever.swift`, `GroundedAnswer.swift`, `AnswerValidator.swift`, `QuestionService.swift` protocol + fake, `Live/LiveQuestionService.swift`), `Features/RecordingDetail/AskTab.swift`, `RecordingDetailView.swift` (tab), `Support/ExportGate.swift` (unlock gate), `docs/EVALS.md`.

**Tests.** Retriever ranking on a synthetic transcript (name bias, neighbour inclusion, chronological order, budget respected, never splits a paragraph); validator (citation inside a retrieved paragraph passes, outside fails, empty citations fail, not-found path); question service with the fake model.

**Device.** Ten questions on the 25-minute recording and the ten on the sample, logged in EVALS with the traps.

**Size.** L. **Verify first.** `GenerationOptions` and `@Generable` on the current SDK (already in use), `LanguageModelSession.respond(to:generating:)` signature for the answer type.

### 12. Chapters

**What.** Topic chapters with start times on the Audio tab, tick marks on the scrubber, and small headings in the transcript, so a 60-minute lecture can be navigated. The general summary already returns topics; this adds when each starts.

**Design.**
- Schema: `KeyPointTopic` gains `startTimestamp: String` with a `@Guide` of "mm:ss of the first line about this subject" (prompt v3). Walk-through `WorkArea` gets the same field so a site walk has a chapter per area. Client summaries derive chapters from the general topic list by adding `topics` to `ClientMeetingSummary` too (same field, same guide).
- Post-processing, pure Swift: parse, clamp to the duration, sort, drop a chapter within 20 seconds of the previous one, and if a start is missing or invalid, fall back to the earliest paragraph that contains two or more words of the topic title (reuse `ActionItemPostProcessor.nearestSegmentStart`). Show chapters only when there are two or more; the first chapter always starts at 0:00.
- Persistence: inside the payload (`topics[i].start: TimeInterval?`), so old payloads decode unchanged and no schema field is needed.
- UI: chapter list under the waveform with title and time, ticks on the scrubber, tap seeks; transcript shows an eyebrow heading before the first paragraph of each chapter; exports list chapters after the overview.

**Files.** `Services/SummaryPayload.swift`, `Services/Live/LiveSummarizationService.swift` (generable mirrors), `Services/Summaries/Prompts.swift`, `ActionItemPostProcessor.swift` or a new `ChapterPostProcessor.swift`, `Features/RecordingDetail/AudioTab.swift`, `TranscriptTab.swift`, `Services/Exports/ExportRenderer.swift`.

**Tests.** Chapter validation table (valid, out of range, unordered, too close, missing with fallback, single chapter hidden); decoding a v2 payload without starts; renderer output.

**Device.** The 25-minute recording and the 60-minute fixture: chapters land within ±30 s of where the subject actually starts (spot-check five per recording, logged in EVALS).

**Size.** M. Ships with prompt v3 (with item 1). **Verify first.** Nothing new.

### 13. Custom templates and a focus line

**What.** Let the user make their own template from the sections that already exist, plus a one-line focus ("pay particular attention to the budget"). Unlocked-only. This is the groundwork for the template packs SPEC §13.4 names as future revenue, without letting the schemas become user-controlled.

**Design.**
- Model: `CustomTemplate` (SwiftData): id, name, symbol, `base: TemplateID`, `hiddenSections: [String]`, `focus: String`, `createdAt`. `Recording` gets `customTemplateID: UUID?`; `templateID` keeps holding the base so every existing switch keeps working.
- Generation: the base template's `@Generable` output is unchanged; the focus line is appended after the shared rules as "The user asked you to pay particular attention to: <focus>" with the focus sanitised (one line, 200 characters, quotes stripped, passed through `TextSanitizer`) so it can't rewrite the rules above it. Hidden sections are removed at render and export time, never from the payload, so un-hiding costs nothing. New section kinds (risks, quotes worth keeping, people mentioned) are a 1.2 schema change once the base-plus-toggles version has been used for a while.
- Focus without a template: the Record screen's template row gains an optional "Focus" line for that recording only (stored on `Recording.focus`); the Change template sheet offers the same. The focus is saved in `modelInfo` so a history entry shows what it was told.
- UI: Settings → Templates lists the three built-ins and the user's own; an editor with name, base picker, section toggles, focus; the Record screen's template picker and the Library filter chips show custom names (the design spec already lists "the user's own template names" as chips).
- Free tier: the editor opens the paywall; built-in templates unchanged.

**Files.** New `Persistence/Models/CustomTemplate.swift`, `Persistence/Models/Recording.swift` (`customTemplateID`, `focus`), `Services/Summaries/Prompts.swift`, `SummarizationInputBuilder.swift`, `Features/Settings/TemplatesView.swift` (+ editor), `Features/Recorder/RecorderView.swift`, `Features/RecordingDetail/SummaryTab.swift` (hidden sections, Change template), `Features/Library/LibraryFilter.swift`, `Support/ExportGate.swift`.

### 14. On-device translation

**What.** Translate a transcript and its summary into another language on the phone with Apple's Translation framework. Unlocked-only. Opens non-English use without touching the privacy promise.

**Design.**
- Framework: `Translation` (iOS 17.4+). A `TranslationSession` is only obtainable through the SwiftUI `.translationTask(_:action:)` modifier, so the transcript screen owns a `TranslationRequest` state and the task calls `session.translate(batch:)` over the segments and, separately, over the summary strings. Language packs are downloaded by the system on demand; that is an Apple asset download, the same class as speech assets, and gets added to SPEC §14.1's allowed list with a DECISIONS entry.
- Data: `TranscriptSegment.translatedText: String?` and `translationLocale: String?` so a translation is done once and survives relaunch; `SummaryRecord.translationsJSON: Data?` holding `[locale: SummaryTranslation]` keyed by the payload's string paths (title, overview, points, tasks, decisions, questions). Action item dates and timestamps are never translated, they're structured.
- UI: Transcript and Summary tabs get "Translate to…" in the more menu; a toggle shows the translation under each paragraph or replaces the text; the target language is remembered. Exports gain "Include translation".
- Availability: `LanguageAvailability().status(from:to:)` decides whether to show the option; unsupported pairs are hidden.

**Files.** New `Services/TranslationService.swift` (protocol + fake, pure batching and mapping), `Features/RecordingDetail/TranslationController.swift` (the `.translationTask` host), `Persistence/Models/TranscriptSegment.swift`, `SummaryRecord.swift`, `TranscriptTab.swift`, `SummaryTab.swift`, `Services/Exports/ExportRenderer.swift`, `Support/ExportGate.swift`.

**Tests.** Batching (segment order preserved, empty segments skipped, results mapped back by index), summary string path mapping round-trip, renderer with translation included, decoding records without the new field.

**Device.** Translate the sample recording to Spanish; pack download progress shows; relaunch and the translation is still there; export a PDF with both languages.

**Size.** M. **Verify first.** `translationTask` and `TranslationSession.translate(batch:)` signatures, `LanguageAvailability`, and whether the framework works while the app is in the background (it shouldn't need to; translation runs in the foreground only).

### 15. Mac first, then iPad

**What.** A native Mac app, then a real iPad layout. Jeremy's order: Mac before iPad. Consultants review and write at a desk, and online-meeting recordings (Teams, Zoom) live on the Mac, so the Mac is where the import path pays off most.

**Why native and not Catalyst.** Mac Catalyst runs the iPad app, so it needs the iPad layout first, which is the wrong order. A native macOS target shares every SwiftUI screen, view model, service protocol and the whole pipeline; only the platform edges differ. Those edges are small and already isolated: `AVAudioSession` is used in three files, UIKit-only export code in three, the iOS 26-only frameworks in four.

**Design.**
- Target: `VeraFlow-macOS` in `project.yml`, macOS 26 minimum (SpeechAnalyzer and Foundation Models arrive on macOS 26; Apple silicon only for the model). Shared sources stay in `VeraFlow/`; platform splits use `#if os(macOS)` or a second file behind the same protocol, never a fork of a screen.
- Recording: `LiveAudioRecorderService` keeps the `AVAudioEngine` tap and format conversion; on the Mac there is no `AVAudioSession`, so the session, route-change and interruption code moves behind a small `AudioSessionPolicy` protocol with an iOS implementation and a macOS one that lists inputs from `AVCaptureDevice` and asks for microphone permission with `AVCaptureDevice.requestAccess(for: .audio)`. Pause/Resume, marks and levels are unchanged.
- Playback: `AudioPlayerController` drops the session call on macOS; Now Playing works through the same `MPNowPlayingInfoCenter`.
- Exports: PDF via a `CGContext` PDF context on macOS (same Core Text layout code), share through `NSSharingServicePicker`, mail through `NSSharingService(named: .composeEmail)`, copy through `NSPasteboard`. Reminders through EventKit as now.
- Not on the Mac: Live Activity and the widget extension, `BGContinuedProcessingTaskRequest` (the Mac just keeps running), Face ID (Touch ID or password via the same `LocalAuthentication` call). The consent sheet stays.
- Layout: `NavigationSplitView` with the Library in the sidebar and the three tabs in the detail; the design's custom header becomes the sidebar header. Keyboard: space play/pause, ⌘F search, ⌘N record, ⌘E edit, ⌘⇧S share, ⌘I import. Drag a file onto the window to import. Menu bar with the same commands.
- Purchase: one app record with **universal purchase** on, so the iPhone unlock covers the Mac. This has to be set up in App Store Connect before the Mac build is uploaded; it cannot be turned on later for a separately created Mac app.
- Diarization models and Parakeet run on the Mac unchanged (Core ML). Verify FluidAudio's macOS minimum against the pinned version.

**Then iPad.** `TARGETED_DEVICE_FAMILY` 1,2. The split layout and keyboard commands built for the Mac apply directly in regular width; compact width keeps the iPhone stack. The Live Activity stays iPhone-only. iPad screenshots become mandatory in App Store Connect the moment iPad is enabled, so `ScreenshotTests` gains an iPad run.

**Files.** `project.yml` (new target), `Services/Live/LiveAudioRecorderService.swift` + new `AudioSessionPolicy.swift`, `Features/RecordingDetail/AudioPlayerController.swift`, `Services/Live/LiveExportService.swift` + `Features/Exports/*` (platform splits), `App/RootView.swift`, `Features/Library/LibraryView.swift`, `Design/VeraFlowComponents.swift`, `VeraFlowUITests/`.

**Tests.** All unit tests run on macOS as well (a second `scripts/test.sh --platform macos` destination); the recorder and player tests use the policy fake. UI tests for launch, import by drag, record, transcript search on the Mac; later the iPad set.

**Device.** Jeremy's Mac: record from the built-in mic and from a USB mic, import a Teams recording, full pipeline, exports, purchase restore with universal purchase in the sandbox. iPad if available.

**Size.** L for the Mac (six to eight days including the platform splits), M for the iPad afterwards. **Verify first.** SpeechAnalyzer, Foundation Models and `BGTaskScheduler` availability on macOS 26; `AVCaptureDevice` input enumeration for an `AVAudioEngine` tap; FluidAudio's macOS platform floor; universal purchase setup steps in App Store Connect.

### 16. Older iPhones: an iOS 18 floor with Parakeet

**What.** Let iPhones that can't run iOS 26 (iPhone XS, XR) and people who haven't updated install the app, transcribe with FluidAudio's Parakeet instead of Apple's speech engine, and get speaker labels. Jeremy's question from the review.

**Two different gaps, stated plainly.**
- **The iOS version gap.** The iOS 26 minimum exists only because `SpeechAnalyzer` is iOS 26. Parakeet is Core ML and runs on much older iOS, so transcription on older phones is possible.
- **The Apple Intelligence gap.** Summaries need the on-device Foundation Models, which need an Apple Intelligence phone (iPhone 15 Pro or newer) **and** iOS 26. Parakeet does not close that gap; it transcribes, it doesn't summarize. An iPhone 15 on iOS 26 and an iPhone XR on iOS 18 both get transcripts and speaker labels and no summaries. The only way to summarize on those phones is a bundled small model (item 17). The app already handles the no-summary case honestly: the capability page, the Summary tab and the paywall all say so.

**Design.**
- Floor: iOS 18 (SwiftData needs 17; 18 keeps the test matrix to two major versions). `project.yml` deployment target 18.0; `@available(iOS 26, *)` on the four iOS 26 files: `LiveTranscriptionService`, `LiveSummarizationService`, `LiveCapabilityService`, `LiveBackgroundProcessing`. Each already sits behind a protocol, so `AppServices.live()` picks the implementation by availability; on iOS 18 the summarizer is an `UnavailableSummarizationService` that reports `.deviceNotEligible`, and background processing uses the inline fallback that already exists.
- Transcription: `ParakeetTranscriptionService` leaves `#if DEBUG` and becomes the engine on iOS 18 through the existing `EngineSelectingTranscriptionService`. On iOS 26 Apple Speech stays the default. Languages: Parakeet TDT v3 covers 25 European languages; the picker (item 8) lists Parakeet's languages on those phones.
- Download: the Parakeet models are a one-time download of roughly 600 MB from the same host as the diarizer. The onboarding capability page says so before the download starts.
- UI: everything else runs as is. Any iOS 26-only SwiftUI modifier that shows up in the compile is wrapped or replaced; the redesign uses the design tokens, not system glass, so this should be small.
- Free/unlocked: unchanged. On those phones the paywall already sells exports and future summaries with clear copy.

**Files.** `project.yml`, `App/AppServices.swift`, the four iOS 26 service files, `Services/Live/ParakeetTranscriptionService.swift`, `Services/EngineSelectingTranscriptionService.swift`, `Features/Onboarding/OnboardingView.swift`, `Features/Settings/SettingsView.swift`.

**Tests.** Engine selection by availability (fake availability provider), the unavailable summarizer's reason, the existing Parakeet benchmark tests move out of DEBUG, network-policy test unchanged.

**Device.** This needs an older iPhone on iOS 18: install, download Parakeet, record five minutes, full transcript with two speakers, no crash and no memory warning. Time and memory logged in DECISIONS. Without that phone the item can't be checked in and should wait.

**Risks.** Parakeet at 0.6B parameters on an A12 phone with 4 GB of memory may be slow or get killed; the device check decides. Two engines means two sets of transcript quirks (Parakeet has no per-word confidence, and its timestamps come from the decoder). FluidAudio's own iOS floor must be verified against the pinned version.

**Size.** M for the code, plus the device check. **Verify first.** FluidAudio 0.15.7 platform requirements; that nothing else in the app calls an iOS 26-only API (compile with the lowered target and read the errors).

### 17. Bundled summary model for phones without Apple Intelligence (investigation only in 1.1)

**What.** SPEC §11.7 names a bundled MLX model as the fallback for phones without Apple Intelligence. This is the real answer to "what if Apple Intelligence isn't there," and it is a bigger decision than 1.1 should take on blind.

**What 1.1 does.** A written investigation, not code: candidate models that fit a 4 GB phone (2 to 3 billion parameters, 4-bit), app size or download impact (1.5 to 2 GB), speed on an A15 or A16 for the 25-minute recording, quality against the Apple model on the same fixtures with the same prompts and the same no-invention rules, and the package it would need (MLX Swift, a second dependency, which CLAUDE.md says needs a written reason). The `SummarizationService` protocol is already the seam; nothing needs to change now to keep the door open. Output: a review in `docs/reviews/` with a go or no-go for 1.2.

**Size.** S for the write-up.
